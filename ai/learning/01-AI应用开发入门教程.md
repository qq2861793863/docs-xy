## 1. LLM 基础（大模型使用）

### 1.1 什么是 Prompt（提示词）

**Prompt** 就是你发给大模型的「指令 + 上下文」。模型不会读心术，它只会根据你给的文字来生成下一段文字。

可以把它理解成：

```
你（用户）写一段话 → 模型读这段话 → 模型续写/回答
```

**案例：**

| 差的 Prompt | 好的 Prompt |
|------------|------------|
| 帮我写个简历 | 你是一名资深 HR，请根据以下经历，生成一份 1 页以内的前端工程师简历，突出 React 和性能优化经验 |

👉 **能力目标**：能控制 AI 的输出风格、长度、语气。

---

### 1.2 三种角色：system / user / assistant

大多数 API 用「消息数组」对话，每条消息有一个 **role**：

| 角色 | 作用 | 类比 |
|------|------|------|
| **system** | 设定 AI 的身份、规则、输出格式 | 给员工的「岗位说明书」 |
| **user** | 用户的问题或任务 | 老板布置的任务 |
| **assistant** | 模型之前的回复 | 员工之前的回答（用于多轮对话） |

**示例（概念）：**

```json
[
  { "role": "system", "content": "你是招聘助手，回答简洁，用中文。" },
  { "role": "user", "content": "张三，5年 Java，熟悉 Spring，请解析成 JSON。" },
  { "role": "assistant", "content": "{ \"name\": \"张三\", ... }" },
  { "role": "user", "content": "再补一个技能：Docker" }
]
```

- **system** 一般只在会话开头放一次，用来「定调子」。
- 多轮对话时，要把历史 **user / assistant** 一起发给 API，模型才能「记住」上文。

---

### 1.3 temperature 与 tokens

**temperature（温度）** — 控制随机性 / 创造力：

| 值 | 效果 | 适用场景 |
|----|------|----------|
| 0 ~ 0.3 | 稳定、可重复 | 提取信息、JSON、分类 |
| 0.7 ~ 1.0 | 更有创意、多样 | 文案、头脑风暴 |
| > 1 | 很发散，容易跑偏 | 一般少用 |

**tokens** — 文本的计费与长度单位（大致：英文 1 词 ≈ 1 token，中文 1 字 ≈ 1~2 token）：

- **输入 tokens**：你发的 prompt + 历史对话
- **输出 tokens**：模型生成的内容
- **上下文窗口**：模型一次能「看」的最大 token 数（如 8K、128K）

👉 对话太长会超出窗口，需要**截断历史**或**摘要压缩**。

---

### 1.4 上下文（Context）

**上下文** = 模型做当前回答时能参考的全部信息，通常包括：

1. system 提示
2. 历史对话
3. 你附加的资料（文档、检索结果等）

```
┌─────────────────────────────────┐
│  System: 你是客服助手...         │
│  User: 订单 123 什么时候到？      │
│  Assistant: 请提供手机号...       │
│  User: 138xxxx                   │  ← 当前问题
└─────────────────────────────────┘
           ↓
        模型生成回答
```

**实践建议：**

- 重要规则放在 **system** 里，不要指望用户每轮都重复。
- 上下文不是越多越好：无关内容会干扰回答、浪费 token。

## 2. Prompt 工程（核心能力）

> 这比「会写代码调 API」重要 10 倍。API 只是管道，Prompt 决定效果。

### 2.1 Few-shot（给例子）

在 prompt 里放 **1~3 个输入输出示例**，模型会模仿格式和逻辑。

**案例：情感分类**

```text
请判断下面句子的情感，只输出：正面 / 负面 / 中性

例1：
输入：这个产品太好用了！
输出：正面

例2：
输入：等了三天还没发货。
输出：负面

现在请分类：
输入：价格还行，质量一般。
输出：
```

---

### 2.2 角色设定

用 system 或开头一句定义身份，能显著提升专业度。

```text
你是一名有 10 年经验的前端架构师，擅长 React 和性能优化。
回答时用条目列表，并给出可落地的代码示例。
```

---

### 2.3 约束输出格式

明确告诉模型「只要 JSON」「不要 markdown」「字段必须齐全」。

```text
你是一个招聘助手，请把下面内容解析成 JSON，不要输出其它文字：
字段：姓名、技能（数组）、年限（数字）

简历内容：
张三，熟悉 Vue/React，工作 5 年。
```

期望输出：

```json
{
  "姓名": "张三",
  "技能": ["Vue", "React"],
  "年限": 5
}
```

---

### 2.4 防止胡说（幻觉）

大模型会**自信地编造**不存在的事实。常用手段：

| 方法 | 说明 |
|------|------|
| 限定知识范围 | 「仅根据下面文档回答，文档没有则说不知道」 |
| 要求引用 | 「回答时标注段落编号」 |
| 降低 temperature |  factual 任务用 0~0.3 |
| RAG | 先检索真实文档再回答（见第 5 节） |
| 校验 | 对 JSON 做 schema 校验，失败则重试 |

**案例：**

```text
你只能使用【参考资料】中的内容回答问题。
如果资料中没有答案，请回复：「资料中未找到相关信息」。
不要猜测，不要编造链接或数据。
```

---

### 2.5 Prompt 模板小结

```text
【角色】你是……
【任务】请……
【格式】输出 JSON，字段：……
【约束】不知道就说不知道；不要编造
【示例】（可选）输入 → 输出
【输入】……
```

## 3. AI API 调用（前端 + Node）

### 3.1 你要会的能力

| 能力 | 说明 |
|------|------|
| 调用 AI 接口 | HTTP + API Key，或官方 SDK |
| 流式输出 | SSE / stream，边生成边显示 |
| 会话管理 | 维护 messages 数组 |
| 错误处理 | 超时、限流、重试、降级 |

---

### 3.2 最小 Node 示例（OpenAI 兼容接口）

> 国内常用：DeepSeek、通义、智谱、Moonshot 等，多数兼容 OpenAI 格式。

```bash
npm install openai
```

```javascript
import OpenAI from 'openai';

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  // baseURL: 'https://api.deepseek.com/v1', // 换厂商时改这里
});

async function chat(userMessage) {
  const response = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '你是简洁的中文助手。' },
      { role: 'user', content: userMessage },
    ],
    temperature: 0.7,
  });
  return response.choices[0].message.content;
}
```

---

### 3.3 流式输出（边生成边显示）

```javascript
const stream = await client.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: '写一首关于编程的短诗' }],
  stream: true,
});

for await (const chunk of stream) {
  const text = chunk.choices[0]?.delta?.content || '';
  process.stdout.write(text); // 前端里 append 到 DOM
}
```

前端通常用 **fetch + ReadableStream** 或 **EventSource（SSE）** 接收。

---

### 3.4 会话管理

```javascript
const messages = [
  { role: 'system', content: '你是客服。' },
];

function appendUser(text) {
  messages.push({ role: 'user', content: text });
}

function appendAssistant(text) {
  messages.push({ role: 'assistant', content: text });
}

// 每次请求把整个 messages 发给 API
```

**注意：**

- 历史过长时：只保留最近 N 轮，或对旧对话做摘要。
- **API Key 永远不要放前端**，应通过你自己的后端转发。

---

### 3.5 错误处理

```javascript
async function chatWithRetry(fn, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await fn();
    } catch (err) {
      const retryable = err.status === 429 || err.status >= 500;
      if (!retryable || i === maxRetries - 1) throw err;
      await new Promise(r => setTimeout(r, 1000 * (i + 1))); // 指数退避
    }
  }
}
```

常见错误：

| 状态码 | 含义 | 处理 |
|--------|------|------|
| 401 | Key 无效 | 检查环境变量 |
| 429 | 限流 | 重试 + 排队 |
| 500 | 服务端错误 | 重试或换模型 |
| 超时 | 网络/响应慢 | 设置 timeout，提示用户 |

### 3.6 练手项目：带业务的 Chat 页面

做一个类似 ChatGPT 的页面，但嵌入你的业务，例如：

## 4. 结构化输出（非常关键）

> **聊天工具**：用户看一段自然语言。  
> **AI 产品**：程序要解析结果 → 填表、搜库、触发流程。

### 4.1 为什么要 JSON

```json
{
  "title": "季度复盘",
  "summary": "本季度 GMV 增长 12%……",
  "tags": ["复盘", "电商"]
}
```

程序可以：

```javascript
const data = JSON.parse(response);
document.querySelector('#title').value = data.title;
renderTags(data.tags);
```

---

### 4.2 三种实现方式

#### 方式 A：Prompt 约束 + 解析（最简单）

```text
只输出合法 JSON，不要 markdown 代码块：
{ "title": "", "summary": "", "tags": [] }
```

解析时处理模型偶尔加的 `` ```json `` 包裹：

```javascript
function extractJson(text) {
  const match = text.match(/\{[\s\S]*\}/);
  if (!match) throw new Error('No JSON found');
  return JSON.parse(match[0]);
}
```

#### 方式 B：JSON Schema / response_format（推荐）

OpenAI 等支持 `response_format: { type: "json_object" }` 或 **Structured Outputs**（严格 schema）。

```javascript
const response = await client.chat.completions.create({
  model: 'gpt-4o-mini',
  response_format: { type: 'json_object' },
  messages: [
    {
      role: 'system',
      content: '输出 JSON，包含 title(string)、summary(string)、tags(string[])。',
    },
    { role: 'user', content: '总结这篇文章：……' },
  ],
});
```

#### 方式 C：校验 + 重试

用 [Zod](https://zod.dev/) / [ajv](https://ajv.js.org/) 校验，失败则把错误信息塞回 prompt 让模型修正。

```javascript
import { z } from 'zod';

const Schema = z.object({
  title: z.string(),
  summary: z.string(),
  tags: z.array(z.string()),
});

function parseAndValidate(raw) {
  const json = extractJson(raw);
  return Schema.parse(json); // 失败会 throw
}
```


## 5. RAG 检索增强生成入门

> 让 AI 基于**你的文档**回答，而不是只靠训练数据「瞎编」。

### 5.1 核心概念

```
用户提问
   ↓
① 把问题变成向量（embedding）
   ↓
② 在向量库里找相似文档片段（chunk）
   ↓
③ 把片段 + 问题一起发给 LLM
   ↓
④ 模型基于片段生成回答（并引用来源）
```

| 概念 | 通俗解释 |
|------|----------|
| **Embedding** | 把文字变成一串数字（向量），语义相近的文字向量距离近 |
| **Chunk（切片）** | 长文档切成小块（如 500 字一块），便于检索 |
| **相似度搜索** | 找和问题最像的几块文本 |
| **引用来源** | 回答里标注「来自第 3 段 / 第 12 页」 |

---

### 5.2 文档切片示例

```javascript
function chunkText(text, size = 500, overlap = 50) {
  const chunks = [];
  for (let i = 0; i < text.length; i += size - overlap) {
    chunks.push(text.slice(i, i + size));
  }
  return chunks;
}
```

**技巧：**

- 按标题 / 段落切，比固定字数更准
- overlap（重叠）避免句子被拦腰截断
- 每块带上 `source`（文件名、页码）

---

### 5.3 RAG Prompt 模板

```text
你是文档问答助手。仅根据【参考资料】回答，并注明引用编号。

【参考资料】
[1] ……chunk 内容……
[2] ……chunk 内容……

【用户问题】
{question}

若资料不足以回答，请说「根据现有资料无法确定」。
```

---

### 5.4 练手项目：PDF 文档问答

**流程：**

1. 用户上传 PDF
2. 解析文本（如 `pdf-parse`）
3. 切片 → 调用 embedding API → 存入向量库
4. 用户提问 → 检索 top-K 片段 → LLM 生成答案

**常用工具：**

| 类型 | 工具 |
|------|------|
| 框架 | [LangChain.js](https://js.langchain.com/)、[LlamaIndex TS](https://ts.llamaindex.ai/) |
| 向量库 | [Chroma](https://www.trychroma.com/)、[Qdrant](https://qdrant.tech/)、[Pinecone](https://www.pinecone.io/)、pgvector |
| Embedding | OpenAI `text-embedding-3-small`、各云厂商 embedding 接口 |
| 本地实验 | [Ollama](https://ollama.com/) + 本地向量库 |

---

### 5.5 RAG 常见问题

| 问题 | 对策 |
|------|------|
| 搜不到相关内容 | 调 chunk 大小、换 embedding、混合关键词搜索 |
| 回答仍幻觉 | 强化「仅根据资料」+ 降低 temperature |
| 速度慢 | 缓存 embedding、减小 top-K、用小模型做检索 |

## 6. AI 产品思维

会调 API 不等于会做产品。需要从用户和业务角度设计。

### 6.1 用户为什么用 AI

先问：

- 用户要解决什么问题？（省时间 / 降门槛 / 个性化）
- AI 比传统方案好在哪里？
- 失败时用户还能完成任务吗？

**反例**：为了 AI 而 AI —— 用户只想导出 Excel，你却做了一个聊天框。

**正例**：粘贴合同 → 自动提取关键条款 → 一键填入审批单（AI 藏在流程里）。

---

### 6.2 AI 出错怎么办

AI **一定会错**。产品设计要预设：

| 策略 | 说明 |
|------|------|
| **可编辑** | 生成结果默认可改，不要锁死 |
| **重试** | 一键重新生成，或换表述再试 |
| **降级** | 模型超时 → 模板 / 人工 / FAQ |
| **确认步骤** | 关键操作（发邮件、下单）要用户确认 |
| **日志** | 记录 prompt / 检索片段，方便排查 |

---

### 6.3 如何给「可信度」

| 手段 | 示例 |
|------|------|
| 展示引用 | 「根据《员工手册》第 3.2 节……」 |
| 置信度提示 | 「以下信息可能不完整，请核对原文」 |
| 分步展示 | 先列检索到的片段，再生成结论 |
| 限制领域 | 「本助手仅回答公司产品相关问题」 |
| 人工入口 | 「转人工客服」按钮始终可见 |

---

### 6.4 是否展示引用 / 是否允许重试

**建议默认：**

- ✅ 知识类 / 合规类：**必须**展示引用
- ✅ 生成类（文案）：允许重试 + 编辑
- ✅ 结构化输出：校验失败自动重试 1~2 次
- ❌ 不要假装 AI 100% 正确

---

### 6.5 产品 checklist

上线前自问：

- [ ] 用户 30 秒内能理解这个 AI 能干什么？
- [ ] 出错时界面有明确提示和退路？
- [ ] 敏感数据是否经过后端、是否脱敏？
- [ ] 延迟是否可接受（流式 / loading）？
- [ ] 成本是否可控（token 上限、频率限制）？

入门阶段可先了解这些方向名称，不必深学：

| 方向 | 入门只需知道 |
|------|--------------|
| **Agent** | AI 能调工具做多步任务 → 中级详学 |
| **MCP** | 统一接 DB/API 的协议 → 中级详学 |
| **评测** | 改 Prompt 要有测试集 → 中级用 promptfoo |
| **微调** | 最后手段，先 Prompt+RAG → 高级详学 |

---

### 7.4 一句话总结

| 层级 | 核心 |
|------|------|
| Prompt | 决定 AI **说什么、怎么说** |
| API | 决定 AI **怎么接入你的产品** |
| 结构化输出 | 决定 AI **能不能驱动业务逻辑** |
| RAG | 决定 AI **能不能基于真实资料** |
| 产品思维 | 决定用户 **愿不愿意用、敢不敢用** |
