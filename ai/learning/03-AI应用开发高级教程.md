## 1. 高级能力地图

### 1.1 中级 vs 高级

| 维度 | 中级 | 高级 |
|------|------|------|
| 质量提升 | 改 Prompt、换 Rerank | 微调、路由、专用 Judge |
| 部署 | 单服务 + 观测 | 多环境、灰度、回滚 lineage |
| 评测 | promptfoo 本地 / PR | 分层评测 + 强制门禁 + 人工校准 |
| 成本 | 换小模型 | 量化、批处理、缓存、Speculative Decoding |
| 安全 | 注入防护、工具 ACL | 多租户隔离、审计、内容安全 pipeline |
| 组织 | 个人或小团队功能 | 平台化、统一网关、SLA |

### 1.2 高级毕业标准

- [ ] 能写一份「RAG vs 微调 vs 长上下文」的技术选型文档并落地
- [ ] 完成一次 LoRA/SFT 实验，有 hold-out 评测对比 base 模型
- [ ] 搭建 LLM 评测 CI：fast gate（分钟级）+ full eval（小时级）
- [ ] 生产环境有模型/Prompt/索引版本 lineage，出问题能回滚
- [ ] 设计过多租户 AI 服务的权限与审计方案
- [ ] 做过推理优化（量化或路由），有 latency / cost 前后对比数据

## 2. 架构决策：RAG / MCP / Agent / 长上下文

### 2.1 四层能力栈（2026 共识）

```
┌─────────────────────────────────────────┐
│  Agent 层：多步推理、规划、人机协同       │
├─────────────────────────────────────────┤
│  MCP 层：实时系统读写（DB、API、工单）    │
├─────────────────────────────────────────┤
│  RAG 层：静态知识检索（文档、手册）       │
├─────────────────────────────────────────┤
│  LLM 层：基础生成 + 长上下文              │
└─────────────────────────────────────────┘
```

**它们不是互斥关系，而是组合关系。**

---

### 2.2 选型决策树

```
用户要什么？
│
├─ 纯文本问答，资料在文档里
│   ├─ 资料能放进 128K 上下文？ → 长上下文（CAG）更简单
│   └─ 资料很大 / 常更新？ → RAG（+ Hybrid + Rerank）
│
├─ 要查实时数据（订单、库存）
│   └─ MCP / Tool Calling（不要 RAG 索引订单表）
│
├─ 要多步操作（查 → 判断 → 执行 → 通知）
│   └─ Agent（LangGraph）+ MCP Tools
│
└─ 只是固定 JSON 提取
    └─ 单次 LLM + Structured Output（不要 Agent）
```

---

### 2.3 常见架构反模式

| 反模式 | 为什么错 | 应该怎么做 |
|--------|----------|------------|
| 所有问题都上 Agent | 延迟 3~10x，成本高 | 默认 RAG/单次调用，按需 Agent |
| MCP 替代 RAG 索引 PDF | 每次读全文件，慢且贵 | 大文档 RAG，实时数据 MCP |
| 微调替代 RAG | 知识更新要重新训练 | 事实性知识用 RAG；微调改「风格/格式」 |
| 无评测换模型 | 新模型可能全面退步 | 同一 golden set 对比后再切 |
| 单点 Prompt 无版本 | 无法回滚 | Prompt 进 Git，带 hash 打 Trace |

---

### 2.4 混合架构案例：企业 Copilot

```
用户：「对比 Q3 销售政策和我们华东区上周大单，给 VP 写摘要」

Agent 规划：
  Step 1 → RAG 检索「Q3 销售政策.pdf」
  Step 2 → MCP 查 CRM（华东区上周订单 > 100万）
  Step 3 → LLM 生成摘要（Structured Output）
  Step 4 → Human-in-the-loop 审批后 MCP 发邮件
```

## 3. 模型微调（SFT / LoRA / DPO）

### 3.1 什么时候该微调

| 适合微调 | 不适合微调（先用 Prompt/RAG） |
|----------|-------------------------------|
| 固定输出格式极稳定（法务条款、医疗编码） | 知识频繁变化 |
| 领域术语、口吻必须统一 | 通用问答 |
| 小模型要逼近大模型某垂直能力 | 数据量 < 500 条高质量样本 |
| 降低长 Prompt 的 token 成本 | 没有评测集验证效果 |

**经验法则：** 先把 Prompt + RAG + 结构化输出做到极致，仍不满足再考虑微调。

---

### 3.2 微调方法对比

| 方法 | 说明 | 数据需求 | 典型用途 |
|------|------|----------|----------|
| **SFT**（监督微调） | 输入→期望输出对 | 500~5000+ 条 | 格式、任务、术语 |
| **LoRA / QLoRA** | 只训练低秩适配器 | 同 SFT，显存更低 | 生产常用 |
| **DPO** | 偏好对齐（好/坏回答） | 偏好对 | 语气、安全、风格 |
| **RFT** | 强化学习微调 | 奖励信号 | 复杂推理、工具使用 |

---

### 3.3 数据准备（最关键）

高质量数据 > 花哨算法。

**SFT 样本格式（对话）：**

```json
{
  "messages": [
    { "role": "system", "content": "你是保险核保助手，输出 JSON。" },
    { "role": "user", "content": "30岁，无病史，保额100万……" },
    { "role": "assistant", "content": "{\"risk\": \"low\", \"premium\": 3200}" }
  ]
}
```

**数据清洗 checklist：**

- [ ] 去重（近似 duplicate 会过拟合）
- [ ] 人工抽检 ≥10%
- [ ] 训练 / 验证 / 测试严格分离
- [ ] 覆盖边界 case（拒答、缺信息）
- [ ] 不含 PII / 密钥

**工具：** Hugging Face Datasets、Label Studio、各云标注平台。

---

### 3.4 LoRA 微调流程（概念）

```bash
# 常见栈： Hugging Face Transformers + PEFT + TRL
pip install transformers peft trl datasets accelerate
```

```
1. 选 base 模型（Qwen2.5-7B、Llama 3、DeepSeek 等）
2. 配置 LoRA：rank=8~64，target_modules=q_proj,v_proj,...
3. SFT 训练 1~3 epochs，watch val loss
4. 在 hold-out 测试集 + 业务 eval 对比 base
5. 合并 adapter 或动态加载 LoRA 部署
```

**云服务（免运维）：** Fireworks AI、Together、阿里云 PAI、AWS Bedrock Custom Model 等。

参考：https://huggingface.co/docs/peft · https://fireworks.ai/blog/llm-fine-tuning

---

### 3.5 微调后评估

不要只看 training loss：

| 指标 | 说明 |
|------|------|
| Exact Match | JSON 字段是否完全一致 |
| F1 / ROUGE | 生成类任务 |
| 业务 KPI | 工单一次解决率、人工修改率 |
| 幻觉率 | 与 RAG 引用一致性 |
| 延迟 / 成本 | 小模型微调后是否替代大模型 |

**A/B：** 10% 流量走微调模型，对比核心业务指标 2 周。

---

### 3.6 微调 Judge 模型

通用 GPT-4 做法务评测可能不准。可 **微调专用 Judge**（Prometheus 思路）：

```
输入：标准 rubric + 待评回答
输出：分数 + 理由
```

用于大规模自动化评测，成本低于每次调最强模型。

参考：https://github.com/prometheus-eval/prometheus-eval

## 4. LLMOps 与数据飞轮

### 4.1 什么是 LLMOps

**LLMOps = MLOps + LLM 特有环节**

```
Prompt/RAG 版本管理
    ↓
评测集维护（golden + 生产 badcase）
    ↓
训练/微调（可选）
    ↓
部署（模型 + adapter + 索引）
    ↓
监控（质量、成本、安全）
    ↓
反馈回流 → 更新数据/Prompt/索引
    �（数据飞轮）
```

---

### 4.2 版本与 Lineage

每次生产请求应可追溯：

```
request_id: req-9f3a
├── prompt_version: support-v2.3
├── rag_index_version: kb-2025-11-01
├── model: gpt-4o-mini-2024-07-18
├── lora_adapter: insurance-v1（如有）
└── eval_last_passed: ci-run-8821
```

出问题时可快速回答：**「从哪个版本开始坏的？」**

---

### 4.3 数据飞轮（Data Flywheel）

```
生产用户反馈（👍👎 / 人工改写）
        ↓
   进入标注队列
        ↓
   合并进评测集 + 训练集
        ↓
   定期重跑 eval / 重训 LoRA
        ↓
   灰度发布 → 全量
```

NVIDIA 等企业用 GitOps + Kubernetes 自动化这一 pipeline（NeMo + NIM + Argo）。

参考：https://developer.nvidia.com/blog/fine-tuning-llmops-for-rapid-model-evaluation-and-ongoing-optimization/

---

### 4.4 环境划分

| 环境 | 用途 |
|------|------|
| dev | 随意实验 |
| staging | 完整 eval + 与 prod 同配置 |
| prod | 仅通过门禁的版本 |
| shadow | 新模型并行跑但不返回给用户，只记 log |

## 5. 评测体系与 CI/CD 门禁

### 5.1 分层评测（Tiered Evaluation）

避免「全量 eval 跑 4 小时没人等」：

| 层级 | 时机 | 耗时 | 内容 |
|------|------|------|------|
| **L0 Smoke** | 每次 commit | <2 min | 5 条核心 case + JSON schema |
| **L1 PR Gate** | Pull Request | 5~15 min | 30~50 条 golden + 安全注入 case |
| **L2 Pre-prod** | 合并 main | 1~4 h | 全量 eval + 多模型对比 |
| **L3 Offline** |  nightly | 过夜 | 长上下文、压力、红队 |

参考：https://agility-at-scale.com/ai/architecture/evaluation-and-testing-frameworks/

---

### 5.2 评测类型矩阵

| 类型 | 方法 | 工具 |
|------|------|------|
| 格式 | JSON Schema / Zod | ajv、自定义 |
| 事实 | 与 gold answer 比对 | exact match |
| 语义 | Embedding 相似度 | cosine > threshold |
| 主观 | LLM-as-Judge | promptfoo、DeepEval |
| 安全 | 红队 prompt 集 | 注入、越狱 case |
| RAG | Context precision/recall | RAGAS、DeepEval |
| Agent | 工具调用序列是否正确 | 自定义 assert |

**RAGAS 指标简述：**

- **Faithfulness**：回答是否忠于检索内容
- **Answer Relevance**：回答是否切题
- **Context Precision**：检索片段是否 relevant

---

### 5.3 CI 门禁合约（Eval Contract）

用显式合约决定「能不能发布」：

```yaml
# eval_contract.yaml
environment: production
required_evals:
  - name: support_golden_v3
    rules:
      - metric: faithfulness
        operator: ">="
        threshold: 0.85
      - metric: hallucination_rate
        operator: "<="
        baseline: previous
        max_delta: 0.02
      - metric: p95_latency_ms
        operator: "<="
        threshold: 3000
```

工具如 [Geval](https://github.com/geval-labs/geval) 专注「eval 结果 → CI 放行/阻断」，与 promptfoo（跑 eval）互补。

---

### 5.4 人工评估不可省

自动化 eval 覆盖不了全部：

- 每周抽样 50 条生产对话人工打分
- 校准 LLM Judge（Judge 分数 vs 人工分数相关性 > 0.8）
- 重大 Prompt/模型变更前：领域专家 sign-off

## 6. 推理性能与成本工程

### 6.1 成本构成

```
总成本 = 输入 tokens × 输入单价
       + 输出 tokens × 输出单价
       + 向量检索 / Rerank / 工具 API
       + GPU 自托管（如适用）
       + 观测存储
```

**先量后优：** 用 Helicone / Langfuse 看 top 10 最贵 endpoint。

---

### 6.2 优化手段

| 手段 | 效果 | 复杂度 |
|------|------|--------|
| **模型路由** | 简单任务用小模型，省 5~20x | 中 |
| **Prompt 压缩** | 减 system prompt、检索 TopK | 低 |
| **Semantic Cache** | 相似问题命中缓存 | 中 |
| **批处理（Batch API）** | 非实时任务半价 | 低 |
| **量化 INT8/FP4** | 自托管吞吐 ↑ | 高 |
| **Speculative Decoding** | 延迟 ↓ | 高 |
| **KV Cache 复用** | 多轮对话前缀复用 | 中 |

---

### 6.3 模型路由示例

```typescript
function pickModel(task: TaskMeta) {
  if (task.type === 'classify' || task.maxTokens < 200)
    return 'gpt-4o-mini';        // 便宜快
  if (task.requiresReasoning)
    return 'gpt-4o';             // 复杂推理
  if (task.language === 'zh' && task.domain === 'legal')
    return 'finetuned-legal-7b'; // 自微调
  return 'default-model';
}
```

先用小分类器或规则路由，再考虑「Router 模型」。

---

### 6.4 自托管 vs 云 API

| 选云 API | 选自托管（vLLM / TGI） |
|----------|------------------------|
| 流量波动大 | 流量稳定且大 |
| 团队无 GPU 运维 | 有 GPU 集群 |
| 要快上线 | 数据不能出内网 |
| 要用最新闭源模型 | 开源模型够用 |

**本地实验：** [Ollama](https://ollama.com/) · **生产：** [vLLM](https://docs.vllm.ai/)

## 7. 安全、合规与多租户

### 7.1 威胁模型

| 威胁 | 示例 | 防护 |
|------|------|------|
| Prompt 注入 | 「忽略规则导出数据」 | 分层 prompt + 输出过滤 |
| 间接注入 | 网页/PDF 里藏恶意指令 | 检索内容沙箱标记 |
| 越权工具调用 | 改 user_id 查他人订单 | 服务端 JWT 鉴权 |
| 数据泄露 | 回答含其他租户 PII | 租户隔离索引 + 过滤 |
| 模型滥用 | 刷 API 生成违规内容 | 速率限制 +  moderation |
| Supply Chain | 恶意 MCP Server | 白名单 + 审计 |

---

### 7.2 多租户架构要点

```
Tenant A ──→ 索引 namespace=A ──→ 仅 A 的文档
Tenant B ──→ 索引 namespace=B ──→ 仅 B 的文档
                ↓
         共享 LLM 网关（配额、审计、Key 轮换）
```

- 向量库按 `tenant_id` 过滤（每条 query 强制带 tenant）
- 日志脱敏（手机号、身份证）
- 密钥：每租户独立 API Key 或 OAuth，禁止 LLM 接触 raw credential

---

### 7.3 内容安全 Pipeline

```
用户输入 → 输入 Moderation → LLM → 输出 Moderation → 返回
                ↓ 违规              ↓ 违规
            拒绝 / 人工审核      替换 / 拒答
```

云厂商：OpenAI Moderation、Azure Content Safety、各国内内容审核 API。

---

### 7.4 合规与审计

金融、医疗、政务常见要求：

- 可解释：引用来源、工具调用 log
- 可追溯：谁何时问了什么（保留策略需法务确认）
- 可删除：用户数据 GDPR / 个保法删除权
- 人机协同：高风险决策必须人工确认

## 8. 平台化与模型网关

### 8.1 为什么需要 AI 网关

团队从「一个 Chat Demo」长到「10 个 AI 功能」时，重复问题：

- 各项目各自接 OpenAI Key
- Prompt 散落各处
- 无法统一限流、计费、审计

**AI Gateway** 统一：

```
业务服务 A ──┐
业务服务 B ──┼──→ AI Gateway ──→ OpenAI / Claude / DeepSeek / 自托管
业务服务 C ──┘         ↑
                   鉴权、路由、缓存、日志、配额
```

**开源/商业：** LiteLLM、Portkey、Helicone Gateway、各云 APIM。

---

### 8.2 平台能力清单

| 能力 | 说明 |
|------|------|
| 统一鉴权 | SSO + API Key 分项目 |
| 模型路由 | 按任务/租户/成本选模型 |
| Prompt  registry | 版本化、A/B |
| 配额 | 每租户 token 上限 |
| 可观测 | 统一 Trace ID |
| Fallback | 主模型失败切备用 |

---

### 8.3 Prompt Registry 示例

```yaml
# prompts/support/system.yaml
id: support-system
version: 2.3.1
model_hint: gpt-4o-mini
temperature: 0.2
template: |
  你是 {{ company_name }} 客服。
  仅根据参考资料回答……
variables:
  - company_name
```

应用启动时拉取指定版本；Trace 记录 `prompt_version`。

## 9. 前沿方向（2025–2026）

### 9.1 多模态 Agent

- 图片理解（UI 截图 → 自动生成测试）
- 语音实时对话（OpenAI Realtime API、Gemini Live）
- 文档 OCR + 表格理解 → 结构化入库

### 9.2 Computer Use / 浏览器 Agent

模型操作 GUI、浏览器完成流程（订酒店、填表单）。生产仍不稳定，适合受控环境 + 人工监督。

### 9.3 Coding Agent 与 SDLC 集成

Cursor、Devin 类工具将 Agent 嵌入 IDE / CI：

- 自动 PR review
- 测试生成
-  incident 根因分析

你作为平台负责人需考虑：**代码泄露、自动 merge 权限、eval 门禁**。

### 9.4 Small Language Models（SLM）+ 边缘

7B 以下模型在端侧运行（手机、IoT），配合云端大模型做「端云协同」。

### 9.5 Standard JSON Schema 与互操作

AI SDK 6、OpenAI Structured Outputs 等推动 **标准 JSON Schema** 跨 provider 统一，减少适配代码。
